# วิเคราะห์และออกแบบการย้าย TruckScale เป็น C# native

## ขอบเขตที่ตรวจ

ตรวจโค้ดใน `D:\YT-Desktop-TruckScale` โดยเน้น `TruckScalePage.tsx`, `QueueSummaryPage.tsx`, `TemplateDashboardPage.tsx`, `services/api.ts`, `types/index.ts` และการเชื่อมต่อ Tauri รวมทั้งตรวจ route และ service ของ booking ใน `D:\YTRC-FastAPI-Backend` เพื่อเทียบ payload ก่อนย้าย โดยไม่แก้โค้ดหรือข้อมูลใน repository ต้นทางและ BE

## โครงสร้างและหน้าที่ของแอปต้นทาง

- `TruckScalePage` เป็นหน้าปฏิบัติการรายวัน มีแท็บเช็คอิน, ชั่งเข้า และชั่งออก ตัวกรองวันที่, Cuplump/USS, สถานะ, ประเภทยาง, ประเภทรถ, ค้นหา และตัวเลือกงานยางรับคืน
- การเปลี่ยนสถานะงาน: รอรถ → เช็คอิน → (Cuplump: เริ่ม/หยุดเทน้ำยาง) → ชั่งเข้า → ชั่งออก → เสร็จสิ้น ระบบรองรับรถหัวลากที่แยกน้ำหนักหัวรถและพ่วง และน้ำหนักรับคืนเข้า/ออก
- หน้าสรุปคิว (`QueueSummaryPage`) แสดงสถิติตามวัน, คิวตามช่วงเวลา, สถานะ, กราฟแยกประเภทรถ/ยาง, ตารางค้นหา/กรอง และมุมมองพิมพ์รายงาน
- มีตัวอ่านบาร์โค้ดแบบ keyboard wedge เพื่อค้นหา booking code แล้วเปิดการทำงานถัดไป และโหลดข้อมูลซ้ำเป็นระยะขณะหน้าเปิด
- หน้า Login/Profile/Notifications เป็นส่วนของแอป TruckScale แยกต่างหาก ใน YTRC-ERP ใช้ session และศูนย์แจ้งเตือนของแอปหลัก จึงไม่ควรสร้างระบบยืนยันตัวตนซ้ำใน RRC
- คำสั่ง Tauri เช่น ย่อ/ขยายหน้าต่าง, เปิด browser และดึง CCTV URL เป็นความสามารถระดับ shell/hardware ของแอปเดิม ไม่ใช่ขั้นตอนบันทึก TruckScale ใน BE ส่วนค่าชั่งของหน้าเดิมกรอกผ่านฟอร์ม ไม่ได้อ่านอุปกรณ์ชั่งโดยตรง

## API ที่ใช้ร่วมกัน

| งาน | Endpoint |
|---|---|
| โหลดคิวรายวัน | `GET /api/bookings?date=YYYY-MM-DD` |
| โหลดประเภทยาง | `GET /api/rubber-types` (สำรอง `/api/master/rubber-types`) |
| โหลดจังหวัด | `GET /api/master/provinces` |
| เช็คอิน | `PATCH /api/bookings/{id}/check-in` |
| เริ่ม/หยุดเทน้ำยาง | `PATCH /api/bookings/{id}/start-drain`, `.../stop-drain` |
| น้ำหนักเข้า/ออก | `PATCH /api/bookings/{id}/weight-in`, `.../weight-out` |
| น้ำหนักยางรับคืนเข้า/ออก | `PATCH /api/bookings/{id}/return-weight-in`, `.../return-weight-out` |

`check-in` บันทึกทะเบียนรถ, ประเภทรถ, แหล่ง/ชนิดยาง, ข้อมูลพ่วง และหมายเหตุ ส่วนขั้นตอนเท/ชั่งและสิทธิ์แก้ไขตรวจโดย BE; native UI จะแสดงข้อความจาก API เมื่อไม่มีสิทธิ์หรือข้อมูลผิดเงื่อนไข ไม่ข้ามการตรวจสิทธิ์

## แผนหน้า native ใน RRC

- เมนู `Cuplump` และ `USS` แยกจากกัน แต่ละเมนูมีหน้า `Truck Scale` และ `Queue Summary` ของหมวดนั้น โดยหน้า WPF ล็อกหมวดข้อมูลให้ตรงกับเมนูที่เปิด พร้อมวันที่, ค้นหา/สแกน booking code, ตัวกรองสถานะ/ชนิดยาง/ประเภทรถ, สรุปจำนวนแต่ละสถานะ, ตารางคิว และปุ่มตามขั้นตอนที่เลือก
- workflow ของ Cuplump มีขั้นเทน้ำยางและตัวนับ Draining; USS ไปขั้นชั่งโดยตรงและซ่อนตัวกรอง/สถิติ Draining
- หน้า `Queue Summary` แยกตามเมนู Cuplump/USS และมีสรุปรายวันตามสถานะและช่วงเวลา, กรอง/ค้นหา, ตาราง และพิมพ์ผ่าน Windows PrintDialog
- กรอกน้ำหนักหัวรถและพ่วงแยกกัน; คำนวณน้ำหนักสุทธิจากน้ำหนักเข้ารวมลบน้ำหนักออกรวมเพื่อแสดงเท่านั้น
- ใช้ timer รีเฟรชคิวทุก 15 วินาทีเฉพาะขณะหน้า RRC เปิด และหยุด timer เมื่อออกจากหน้า
- คง source repository และ BE เดิม ไม่แก้/ไม่ push BE ในงานนี้

## ข้อจำกัดของข้อมูลต้นทาง

การแยก “ยาง 2 เบอร์” ใน React สร้าง booking รถพ่วงเพิ่มด้วย id สังเคราะห์ และกลืนข้อผิดพลาดหาก BE ปฏิเสธคำขอ ทำให้ข้อมูลที่เห็นในหน้าจออาจไม่ได้ถูกบันทึกจริง การย้าย C# จะใช้ฟิลด์ `trailerRegister`, `trailerRubberSource`, `trailerRubberType` ที่ BE เช็คอินรองรับบน booking เดียว จึงไม่สร้างคิวเทียม หากต้องการคิวหัว/หางเป็นคนละระเบียนจริง ต้องกำหนด schema/transaction ใน BE ก่อน
